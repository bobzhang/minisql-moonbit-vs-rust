MoonBit and Rust building the same database engine

An AI coding agent built a SQLite-compatible SQL engine nine milestones deep, three times in Rust and three times in MoonBit. This report covers how the experiment was run, what it found, and where MoonBit could remove the extra cost it still pays.

Summary

Parity on agent cost, less code in MoonBit, and a clear list of fixable frictions

  • Agent cost is a draw. MoonBit's mean cost was 0.94× Rust's and its median 1.12×. Three trials cannot separate the two languages; run-to-run variation is larger than the language difference.
  • MoonBit writes less. 12% fewer output tokens and 12% fewer source tokens for the same test results, mostly because it needs no borrows, ?, Result wrapping or cross-module pub.
  • Its extra costs are small and identifiable. The primer re-read on every call (about $1.40 per trial), language-specific compile errors (about 11 extra calls per trial), and about 500 lines per trial of helpers that Rust's standard library provides, led by an ordered map.
  • Most of those costs can be removed by core-library additions, a few targeted compiler messages, and a compact official guide for agents. Section Recommendations ranks them with evidence.
The experiment

One spec, one test suite, two languages

The task was minisql: a command-line engine that reads a SQL script on stdin and prints results, matching SQLite 3.53. It had to reach about 20,000 lines so that the one-time cost of an unfamiliar language would be spread over real work; the finished engines came out at about 13,000 lines.

How sessions ran

  • One fresh headless claude -p session per milestone, in the same workspace
  • Tools: Bash, Read, Edit, Write only; no web, memory, skills or MCP servers
  • Up to 2 follow-up prompts if visible tests still failed (never needed)
  • Rust and MoonBit trials ran in parallel pairs

Fairness controls

  • Identical spec, tests, prompts, model and effort
  • Standard library only; no FFI, no C, no SQLite; checked after every milestone
  • Identical five-function I/O module in both starter projects, since MoonBit core has no stdin or file access
  • Primers with the same four sections: 11.7k tokens for MoonBit, 2.9k for Rust

What was measured

  • Tokens by type, estimated cost, calls, turns and wall time
  • Tokens until the visible tests first all passed
  • Hidden-test pass rate after every milestone
  • Source size in the model's own tokenizer; compile errors from transcripts

Time

Wall time follows output tokens, not compile speed

About 93% of every trial's wall time was the model generating text. Builds, tests and every other command took 8–14 minutes of 2–3 hours. The middle trials make the point: Rust t2 produced 780k output tokens in 2.04 h of model time; MoonBit t2 produced 757k in 2.03 h; both took 2.19 h of wall time. On this project MoonBit's native release build was slower than Rust's (7–9 s vs 3–4 s), while moon check was faster than cargo check (0.2 s vs about 1 s). Neither difference moved the totals.

Compile errors

Every failed build across the six trials was labelled by hand with one primary cause. About half of MoonBit's failures were language-neutral: the primer told agents to run moon check after every edit, so they checked half-written code (198 checks against 3 cargo check runs). Runtime and builds

MoonBit engines ran 1.25× Rust's time and used far less memory

Ten controlled workloads were run on all six finished engines (5 runs each; every output matched SQLite). Bars show MoonBit's time ÷ Rust's, averaged over the three trial pairs, for the whole workload including a shared 300k-row setup. MoonBit was faster on string functions and printf and slowest on index builds and text sorting.

A profile of the index build (MoonBit 5.1 s vs Rust 2.4 s) put about 35% of MoonBit's time in memory management, 22% in reference-count release alone, and about half in the agents' hand-written AVL tree with closure comparators. The slowdown traces mostly to the missing ordered map, not to code generation. Two MoonBit engines implemented index-ordered LIMIT pushdown on their custom trees and were the only engines to pass perf_order_by_limit; all three Rust engines timed out on it.

What worked well

Where MoonBit's design paid off

  • Error effects shrink error-heavy code. The SQLite file reader was 39% fewer tokens than Rust's: raise in 12 signatures replaced 14 ?, 12 Ok/Err, 7 Result types, 43 borrows and 7 lifetimes.
  • No ownership errors. Rust lost 4 builds and 8 calls to the borrow checker; MoonBit has no equivalent class of error.
  • Fast checks and good lookups. moon check in 0.2 s made check-after-every-edit cheap, and moon ide doc answered 25 of 26 queries.
  • Helpful deprecation messages. Every deprecation named its replacement, and no deprecated API remained in any final workspace.
  • Lean binaries. 20–25% smaller binaries and 3.5× lower peak memory on the index workload; string-heavy code ran faster than Rust's.
Recommendations

Where MoonBit can improve, ranked by measured impact

Savings are per nine-milestone trial, estimated from this run. One API call costs about 150–250k cached input tokens plus 0.5–1.5k output tokens.

  1. A complete ordered map in core

    core library≈7k output tokensup to 3× faster index work

    Add open, exclusive and unbounded ranges, reverse iteration, lower/upper bound or seek, first/last and pop_first/pop_last, and a comparator constructor (or a documented key newtype). A B-tree implementation would help cache locality.

    Evidence: all 3 trials wrote a 252–316-line map; SortedMap::* was queried 5 times for methods that don't exist; about half of index-build time was in the hand-written tree.

  2. Targeted messages for common foreign-language forms

    compiler≈6 calls, ≈1M input tokens

    Say "using is a keyword; rename it" and suppress the package-not-found cascade; suggest a fix for let (mut a, b) or accept it; for fn(x) raise E -> T, say "write -> T raise E".

    Evidence: 11 primary failures and 19 calls, in every trial.

  3. Accept C(..) for positional constructors, and coerce non-raising functions to raising function types

    language≈2–3 calls

    B(..) already works for labelled payloads, and eta-expansion is always valid, so both would remove surprises without changing meaning.

    Evidence: 5 involved failed builds.

  4. Float formatting with precision and exponent, plus integer width padding

    core library≈3k output tokensremoves a rounding risk

    For example Double::to_fixed(p), to_exponential(p), or a small format with width and precision.

    Evidence: 74–83 lines of digit generation per trial (double-double or bignum), where Rust used one line.

  5. An official, compact, versioned guide for agents, and current training data

    docs≈2M input tokens if halved

    Cover the pitfalls this primer missed (using, tuple mut, C(..), effect order, raise-polymorphic higher-order functions) and keep it short. A stable syntax matters as much as more data, because mixed old and new forms in training data lead models to write removed forms.

    Evidence: the 11.7k-token primer cost 3.8M extra input tokens per trial, more than all compile errors; its stale-syntax list prevented every error it named.

  6. Diagnostics that survive filtering

    toolchain≈3 calls

    Print errors after warnings or add an errors-only mode; end with a one-line summary of the first error; collapse long help texts such as fragile_catch_all's 12 lines; reconsider the reserved_keyword warning for alias and local.

    Evidence: agents filtered 368 of 376 build outputs through grep/tail; 4 errors were hidden; alias warnings at 46 sites prompted renames that broke 3 builds.

  7. Small adapters around the UTF-16 and integer design

    core library≈2k output tokens

    UInt16 ASCII predicates, a code-point-order string compare (or clear docs that lexical_compare is by code unit), Int64 checked or overflowing arithmetic, and stable_sort_by. UTF-16 strings and wrapping integers are reasonable designs, and string-heavy code ran fast; the cost here is only the missing adapters.

    Evidence: 100–150 hand-written lines per trial.

  8. Less reference-counting overhead on hot paths

    runtime1.4–3.4× on index, sort and window work

    Borrowed parameters or elided drops for comparator arguments, and cheaper comparisons of array keys, while keeping the low memory use.

    Evidence: 22% of samples in moonbit_drop_object and about 35% in memory management on the index workload.

Smaller items

Make unused_mut on a field a warning rather than an error; let while true without break diverge so no nobreak is needed; let moon ide outline accept several paths; print #alias(..., deprecated) attribute lines after signatures in moon ide doc; and look at native release build time, which was about twice cargo's here.

Limits and next steps

What this does not show, and how to firm it up

Limits

  • Three trials per language; mean and median disagree on which language cost less
  • One model, one harness, one kind of program
  • A single-threaded, data-structure-heavy engine suits garbage-collected languages; concurrency and memory control were not tested
  • Compile-error causes were labelled by hand
  • Output tokens cannot be split at the first-green point from the transcripts

Next steps

  • Three more trials per language to roughly halve the uncertainty
  • One MoonBit trial without the primer, to measure what current models know unaided
  • Rerun the same benchmark on each new model generation and track the ratio
  • Rerun after core-library additions to measure recommendations 1, 4 and 7 directly
